<objective>
Close two independent, previously-undiscovered UAT gaps found during phase-02 retesting (neither overlaps
02-04's fix, which addressed G-02-1/G-02-3's load-state precedence in the same file).

**G-02-4 (minor):** the watchlist row's remove (x) button's clickable hit box is exactly the bare 14px glyph
— no padding, background, or border — well under WCAG 2.5.8's 24x24px minimum target size. Root cause:
`frontend/components/WatchlistRow.tsx:109-118`'s `className="text-sm text-[var(--color-down)]"` never adds
size/background. This is a design-contract gap, not an implementation deviation: `02-UI-SPEC.md:148`
specified only the glyph's typography/color and never specified a hit-area or resting-state affordance. The
user explicitly asked for a permanent visible treatment ("stand out from the surrounding background"), not
hover-only — this is a settled requirement from `.planning/debug/remove-button-hit-area-g02-4.md`, not an
open question to re-litigate.

**G-02-5 (major):** the watchlist panel has no height bound (`frontend/components/Watchlist.tsx:92`, no
`max-h-*`/`overflow-y-auto`), so it grows unbounded and the whole page scrolls instead of the panel. A second,
coupled defect: `frontend/app/page.tsx:43`'s row (`flex flex-col gap-4 lg:flex-row`) defaults to
`align-items: stretch` at the `lg:` breakpoint, and `frontend/components/MainChart.tsx:41`'s `PanelChrome`
root sets `h-full` — so the chart's bordered box inherits whatever height the watchlist panel grows to (its
drawn content stays fixed at 320px; only the empty space around it grows). Per
`.planning/debug/watchlist-scroll-chart-height-g02-5.md`'s `and_gate` analysis, both the height bound and the
stretch decoupling are independently required — bounding the watchlist alone only masks the coupling (and can
reverse it, stretching the watchlist to match the chart instead, if the cap lands below the chart's natural
height).

**Deliberate deviation from the diagnosis's literal fix location, recorded so it reads as intentional:** the
G-02-5 debug session's `missing` list names `Watchlist.tsx:92` (the outer bordered panel div, which also
wraps the add-ticker form) as where to add `max-h-*`/`overflow-y-auto`. This plan instead adds a new inner
wrapper around only the loading/loadError/empty/table branch, leaving the add-ticker `<form>` and its error
slot outside the scrollable region. This preserves the already-established, spec-documented product intent
that "the add-ticker form itself always stays visible above" the list (02-UI-SPEC.md's empty-state UI
consideration row) — under the diagnosis's literal placement, scrolling down through a long watchlist would
scroll the add-ticker form out of view too, which is worse UX than the debug session's placement note
anticipated. The underlying truth ("panel scrolls internally, not the page") is satisfied either way.

Purpose: Make the remove control reliably clickable on the first try, and make the watchlist panel's row
count fully independent of both page scroll and the main chart's box height — closing both gaps together
since they are small, independent CSS/layout fixes discovered in the same retest pass. See
`.planning/debug/remove-button-hit-area-g02-4.md` and `.planning/debug/watchlist-scroll-chart-height-g02-5.md`
for full root-cause evidence.
Output: `WatchlistRow.tsx` with a 24x24px accessible remove hit box; `Watchlist.tsx` with a bounded, internally
scrolling list region; `page.tsx` with the chart/watchlist height coupling removed; `Watchlist.test.tsx` with
new coverage for all three; `02-UI-SPEC.md` amended to describe the corrected contracts.
</objective>
