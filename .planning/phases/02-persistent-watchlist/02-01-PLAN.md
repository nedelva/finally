<objective>
Give the terminal a memory: stand up the SQLite persistence layer, serve the watchlist over
`GET /api/watchlist`, and make the browser's watchlist grid render from that response instead of
from the SSE stream's ever-growing ticker set.

This is the phase's tracer slice. It wires one path — SQLite file → `app/db` → `app/api` → HTTP →
`Watchlist.tsx` — end to end, production-quality, before any mutation route is added. When it lands,
**ROADMAP success criterion 3 is already true**: reloading the browser shows the watchlist that lives
in the database. Plans 02-02 (add) and 02-03 (remove) expand outward from this proven path.

**Requirements attribution — read this before crediting coverage.** This plan's frontmatter lists
both `WTCH-01` and `WTCH-02` because it establishes the persisted, REST-served watchlist that both
requirements build on — but it **implements neither user action**. "User can add a ticker manually"
(WTCH-01) lands entirely in plan 02-02; "user can remove a ticker manually" (WTCH-02) lands entirely
in plan 02-03. What this plan delivers against is ROADMAP success criterion 3 (reload shows the
user's own watchlist). Do not mark either requirement satisfied on this plan alone.

Purpose: every later phase's state (positions, trades, snapshots, chat) lands in the schema created
here, so the schema is built once, now, per the roadmap scope note.
Output: `backend/app/db/` and `backend/app/api/` packages, `app/market/ticker.py`, a database-driven
app lifespan, and a REST-driven watchlist grid.

user-story form, and this plan does not invent one. The goal is carried verbatim above. Run
`/gsd mvp-phase 2` if a formal user story is wanted before execution.
