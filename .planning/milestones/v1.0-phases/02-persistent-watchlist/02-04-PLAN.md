<objective>
Fix the single underlying defect behind gaps G-02-1 (watchlist shows empty on load) and G-02-3 (a failed
initial `GET /api/watchlist` produces no visible error): `frontend/components/Watchlist.tsx:31` destructures
only `{ watchlist, refetch }` from `useWatchlist()`, discarding the hook's already-correct `error`/`loading`
fields (`frontend/lib/hooks.ts:77-107`). A successful-empty response and a failed-fetch response currently
render byte-identically. This plan makes the three states — loading, load-failed, genuinely-empty —
visually distinct, restores the UI-SPEC's approved "empty state shown only if the user removes every
ticker" contract, and adds regression coverage for both new states plus the local/hook error-slot
independence.

**Scope boundary:** `frontend/lib/hooks.ts` is correct today and is NOT modified by this plan.
`useWatchlist()` already captures `loading`/`error` correctly; this plan only wires the existing values into
the render. Two things flagged in the debug sessions' own "fix direction" notes are explicitly OUT of scope
here because they appear in neither gap's `missing` list: (1) adding retry/backoff to `useWatchlist()` for a
failed fetch, and (2) deduplicating the two independent `useWatchlist()` call sites (`app/page.tsx:12` and
`Watchlist.tsx:31`). Do not touch `hooks.ts`. Relatedly: `refetch()` never resets `loading` back to `true`,
so the loading branch below fires only on initial mount, not on every `refetch()` call (add/remove/manual
retry) — this is the hook's existing, correct behavior and must not be changed as part of this task, or
every add/remove would incorrectly flash the loading state over the whole grid.

**Deliberate trade-off, recorded so it reads as intentional, not an oversight:** the precedence order below
makes `loadError` win over a populated table. Today, a failed `refetch()` after a prior successful load
silently discards the error and leaves the table showing the last-good watchlist. After this plan, that same
failure replaces a working, populated grid with an error banner — and since `useWatchlist()` has no retry,
this is terminal for the session until a full reload succeeds. This is instructed by the gap's own
`missing` list ("3-way render precedence: loading -> loadError -> watchlist.length === 0 -> table") and is
accepted here as the simplest correct fix for the common case (initial-load failure, watchlist still empty);
a "keep stale data visible, show error as a toast" alternative is out of scope for this fix.

Purpose: Close G-02-1 and G-02-3 together since they are the same code defect observed from two angles
(a naturally-occurring failure vs. a deliberately forced one) — see `.planning/debug/watchlist-empty-on-load.md`
and `.planning/debug/watchlist-load-error-silent.md` for the full root-cause investigation.
Output: `Watchlist.tsx` with a 3-way load-state render precedence; `Watchlist.test.tsx` with new coverage
for the loading and load-error states and a regression guard proving the two error slots do not collide.
</objective>
