Stage 1, named `frontend-builder`, `FROM node:20-slim`: copy `frontend/package.json` and
`frontend/package-lock.json`, run `npm ci`, copy the rest of `frontend/`, run `npm run build`. The
Next.js config already sets `output: "export"`, so the artifact is `frontend/out/`.

Stage 2, `FROM ghcr.io/astral-sh/uv:python3.12-trixie-slim`: create a system group and user both
named `nonroot` with gid/uid 999. Set `WORKDIR /app` and
`ENV PYTHONUNBUFFERED=1 UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy`. Copy
`backend/pyproject.toml` and `backend/uv.lock` to `/app/backend/`, then run `uv sync --locked
--no-install-project` from `/app/backend` so the dependency layer caches independently of source
changes. Then `COPY backend/ /app/backend/` — **preserve the `backend/` subdirectory; never flatten
it into `/app/`**, because `backend/app/db/connection.py` computes `parents[3]` and
`backend/app/main.py` computes `parents[1]`/`parents[2]` off their own physical location. Copy the
stage-1 export with `COPY --from=frontend-builder /app/frontend/out /app/backend/static` (adjust the
source path to wherever stage 1 put `out/`). Run `uv sync --locked` again to install the project.

Add three build-time assertions, each as its own `RUN`, all placed after the source and static
copies:
  1. `RUN test -f /app/backend/static/index.html` — a botched static copy otherwise yields a
     container that answers `/api/health` with 200 while serving zero UI, because
     `resolve_static_dir()` only logs a warning when it finds nothing.
  2. A `RUN` that executes the real resolver with the escape hatches **explicitly unset** —
     `env -u FINALLY_DB_PATH -u FINALLY_STATIC_DIR` running a short Python expression that imports
     `app.db.connection.get_db_path` and asserts it equals `/app/db/finally.db`. With the env pins
     in effect this assertion would pass trivially and prove nothing; unsetting them is what
     actually tests the `parents[N]` arithmetic against the image layout.
  3. The same shape for `app.main.resolve_static_dir`, asserting `/app/backend/static`.

After the assertions: `RUN mkdir -p /app/db && chown -R nonroot:nonroot /app/db /app/backend` —
this must come BEFORE `USER nonroot`, because Docker seeds a brand-new named volume from the image
directory's contents and ownership, and a root-owned `/app/db` makes the first SQLite write fail
under a non-root process.

Then set `ENV PATH="/app/backend/.venv/bin:$PATH"`, `ENV FINALLY_DB_PATH=/app/db/finally.db`,
`ENV FINALLY_STATIC_DIR=/app/backend/static` (belt-and-suspenders on top of the now-proven
arithmetic), `USER nonroot`, `WORKDIR /app/backend`, `EXPOSE 8000`, a `HEALTHCHECK` with
`--interval=10s --timeout=3s --start-period=15s --retries=3` running a Python one-liner that opens
`http://localhost:8000/api/health` via `urllib.request` (the slim images ship no `curl`, and adding
it purely for a healthcheck grows the image for no functional gain), and
`CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]`.

Never add a `COPY .env` or any instruction that reads the operator's secrets at build time —
secrets arrive only at `docker run` via `--env-file`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host filesystem → Docker build context | Everything not excluded by `.dockerignore` becomes copyable into a distributable image layer, including `.env` and `db/finally.db` |
| operator shell → container runtime | `--env-file` carries live API keys across this boundary at run time; they must never cross the build-time boundary |
| container process → host kernel/filesystem | The uvicorn process's uid determines what a container escape or a mounted-volume write can reach |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Information Disclosure | Docker build context / image layers | high | mitigate | `.dockerignore` excludes `.env`, `db/*.db`, `db/*.db-wal`, `db/*.db-shm`, `db/*.db-journal`, `.git`, `.planning`; no `COPY .env` instruction exists; secrets enter only via `--env-file` at `docker run`. Verified by the Task 1 image-layer scan asserting a count of `0`. |
| T-05-02 | Elevation of Privilege | Stage-2 runtime user | high | mitigate | A system user `nonroot` (uid/gid 999) is created and `USER nonroot` is set before `CMD`; `/app/db` and `/app/backend` are `chown`ed to it beforehand so no runtime privilege is needed to write the database. Verified by `docker image inspect --format '{{.Config.User}}'` returning `nonroot`. |
| T-05-08 | Spoofing | Base image provenance | medium | accept | Base images are the official `node:20-slim` (Docker Official Images) and `ghcr.io/astral-sh/uv:python3.12-trixie-slim` (Astral's own GHCR namespace, the pattern Context7 documents). Accepted rather than digest-pinned: this is a locally-built, locally-run educational artifact with no registry-published image, and digest pinning would freeze security patches in a project whose stated deployment story is `docker build` on the operator's own machine. |
</threat_model>
