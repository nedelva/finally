## Layout & Panel Integration

**Design decision (no CONTEXT.md to draw from):** PLAN.md §10 specifies the AI chat panel as a "docked/collapsible sidebar." The current `frontend/app/page.tsx` renders `<Header>` full-width, then a flat vertical stack of panels (`Watchlist`+`MainChart` row → `TradeBar` → `PositionsTable`+`Heatmap` row → `PnLChart`) inside `<main className="flex min-h-screen flex-col gap-4 p-8">`. This phase restructures that stack, not any individual panel:

1. `<Header>` stays exactly as-is, full-width, first in document order — unchanged by this phase.
2. Below the header, wrap the existing panel stack and the new `ChatPanel` in a single row container: `flex flex-col gap-4 lg:flex-row lg:items-start` (the same responsive row idiom already used for the two existing two-column rows).
3. **Left column** (`flex-1 min-w-0` at `lg:`, full width below `lg:`): the entire pre-existing panel stack, unchanged internally — `Watchlist`+`MainChart` row, `TradeBar`, `PositionsTable`+`Heatmap` row, `PnLChart`, in that order, each keeping its current internal layout.
4. **Right column** (`ChatPanel`, `w-full lg:w-96 lg:shrink-0`): docked at `lg:sticky lg:top-8 lg:self-start lg:max-h-[calc(100vh-4rem)]` so it stays in view while the left column scrolls past it on tall viewports. Below `lg:`, it drops to a normal full-width block at the bottom of the vertical stack (same responsive collapse already used by the two existing two-column rows) — no sticky behavior on small screens.

**Collapse mechanism — Design decision (no CONTEXT.md to draw from):** collapse toggles panel *height*, not width, and needs no separate "slim rail" concept:
- **Expanded** (default on every fresh page load — no persistence, see below): renders the full panel — header row, scrollable message list, message input row.
- **Collapsed**: renders only the header row (title + toggle button); the message list and input are not rendered. Panel height shrinks to the header's own height (~48px).
- The toggle is a plain text button in the panel header, not an icon, per this project's no-icon-library convention: label reads `"Hide"` when expanded, `"Show"` when collapsed (exact copy in the Copywriting Contract table).
- Collapse state lives in local component state only — **not persisted** to `localStorage` or any backend field. Every fresh page load starts expanded. This is a deliberate scope-minimization choice: nothing in CHAT-01…06 requires the collapse preference to survive a reload, unlike conversation history (CHAT-06), which is a separate, backend-persisted concern.
- Collapsing/expanding never clears conversation state — the message list and any in-flight request continue to exist underneath; a collapsed panel that finishes loading a response updates its (hidden) state normally and is visible again the next time it's expanded.

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from `03-UI-SPEC.md`, carried forward:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-free inline gaps (e.g. between a pill's leading status glyph and its text) |

| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0d1117` (`--color-bg`) | Page background; also the chat message-list scroll area background |
| Secondary (30%) | `#161b22` (`--color-panel`) / `#30363d` (`--color-border`) | Panel chrome (header row, input row), assistant message bubbles |
| Accent — Brand | `#ecad0a` (`--color-accent-yellow`) | App wordmark only — unchanged, no new use this phase |
| Accent — Primary | `#209dd7` (`--color-primary-blue`) | User message bubble tint/border, input focus ring — same role as elsewhere (chart stroke, focus ring, selected-state tint) |
| Accent — CTA | `#753991` (`--color-secondary-purple`) | **New use this phase:** the chat Send button. Phase 3 restricted purple to the existing "Add Ticker" button and explicitly deferred further use; this phase extends it to the chat form's submit action, consistent with PLAN.md's own definition of purple as "submit buttons" generally (not a Phase-3-only restriction) |
| Positive semantic | `#16a34a` (`--color-up`) | Executed-action confirmation pills (trade fill or watchlist change), reusing the same green already load-bearing for buy/profit elsewhere |
| Destructive/negative semantic | `#dc2626` (`--color-down`) | Failed-action confirmation pills, all chat error-slot text (history-load failure, send failure) |

Accent reserved for: yellow → wordmark only (no change); blue → chart line stroke, input focus rings (trade bar + **new:** chat input), selected-state background tint, user message bubble tint/border; purple → "Add Ticker" button (Phase 2/3) and **new:** chat Send button — both are the project's only two form-submit buttons, keeping "purple = submit" a single consistent rule rather than one-off.

**Design decision (no CONTEXT.md to draw from):** executed vs. failed action pills use the same green/red pair for *both* trade and watchlist actions (not a third color for watchlist changes) — "green = succeeded, red = failed" is a single universal semantic already established by the buy/sell button colors, and introducing a third color for watchlist-specific confirmations would compete with, rather than reinforce, that existing rule.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA — Send | "Send" (relabels to "Sending…" while a request is in flight, matching the existing verb+ellipsis convention — `"Adding…"`, `"Buying…"`, `"Selling…"`) |
| Collapse toggle | "Hide" (expanded → collapsed) / "Show" (collapsed → expanded) |
| Input placeholder | "Message FinAlly…" |
| Empty state — first-ever visit (no chat history) | Seed greeting rendered as the first assistant bubble: "Hi, I'm FinAlly. Ask me about your portfolio, or tell me to buy, sell, or update your watchlist." (rendered locally, not persisted as a `chat_messages` row — the *first real* exchange is what gets persisted) |
| Loading indicator (awaiting LLM response) | "Thinking…" rendered as an assistant-style bubble with `animate-pulse`, matching the app's existing verb+ellipsis loading convention (`"Loading watchlist…"`, `"Waiting for data…"`) |
| Loading — history fetch | "Loading conversation…" placeholder inside the message list, mirroring `Watchlist.tsx`'s `"Loading watchlist…"` row pattern |
| Error state — history fetch failed | "Couldn't load conversation history — you can still send new messages." (shown as a banner above the message list; the seed greeting still renders underneath so the panel is never blank) |
| Error state — send failed (network/server) | "Message not sent — check your connection and try again." (shown in the same error-slot pattern as `TradeBar`'s `trade-bar-error`; the typed message is **not** cleared from the input, so the user can retry without retyping) |
| Trade action — executed | "Bought {quantity} {ticker} @ {price}" / "Sold {quantity} {ticker} @ {price}" — verbatim reuse of `03-UI-SPEC.md`'s trade-fill confirmation copy for consistency across manual and AI-initiated trades |
| Trade action — failed | "Buy {ticker} failed — {error}" / "Sell {ticker} failed — {error}", where `{error}` is the server's own validation message verbatim (e.g. "Insufficient cash for this trade. Lower the quantity and try again.") — CHAT-05's "conversational explanation of the failure" is the assistant's own `message` text; this pill is the mechanical status confirmation alongside it |
| Watchlist action — executed | "Added {ticker} to watchlist" / "Removed {ticker} from watchlist" |
| Watchlist action — failed | "Add {ticker} failed — {error}" / "Remove {ticker} failed — {error}" |
| Destructive confirmation | None — AI-initiated trades and watchlist changes execute instantly with no confirmation dialog, per PLAN.md §2/§9 and `REQUIREMENTS.md`'s Out of Scope table (unchanged carry-forward from `03-UI-SPEC.md`, extended here to cover chat-initiated actions specifically) |

## UI Considerations

Applicable state considerations resolved: 8 covered, 5 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Chat message list (list-collection) — first-ever visit | ✅ covered | Renders the seed greeting bubble instead of a blank panel; copy in Copywriting Contract |
| empty | Message input (form) | ✅ covered | Send button disabled when the input is blank or whitespace-only; Enter key is a no-op on empty input |
| loading | Chat history fetch (list-collection) | 🧪 backstop | Reuses `Watchlist.tsx`'s loading-row pattern verbatim ("Loading conversation…") inside the message area while `GET /api/chat/history` is in flight |
| loading | Chat response (list-collection) | ✅ covered | "Thinking…" assistant-style bubble (`animate-pulse`) appears immediately on send and is replaced by the real response; input and Send button disabled during the window, Send relabels "Sending…" |
| error | Chat history fetch (list-collection) | 🧪 backstop | Banner above the message list per Copywriting Contract; does not block sending; seed greeting still renders underneath so the panel is never blank on failure |
| error | Send message (form) | ✅ covered | Network/server failure on `POST /api/chat` surfaces the error-slot copy below the input, mirroring `TradeBar`'s `trade-bar-error` pattern; typed message is preserved, not cleared |
| populated | Chat message list (list-collection) | ✅ covered | User bubbles right-aligned (blue-tinted per Color contract), assistant bubbles left-aligned (panel-shaded); newest message auto-scrolls into view on send and on response arrival |
| populated | Inline action confirmations (list-collection) | ✅ covered | Each executed action renders as a green pill beneath its assistant message; each failed action renders as a red pill with the server's own error text — copy in Copywriting Contract |
| partial | Mixed-result actions within one turn (list-collection) | 🧪 backstop | A single assistant turn can contain both executed and failed actions (e.g. watchlist add succeeds, same-turn buy fails per 04-RESEARCH.md Pitfall 2 — no live price yet); pills render independently per action in the backend's dispatch order (watchlist changes, then trades), no batching or summary line collapses them |
| overflow | Chat message list (list-collection) | ✅ covered | Reuses `watchlist-scroll-container`'s `max-h` + `overflow-y-auto` pattern — the panel scrolls internally rather than growing the page |
| overflow | Long assistant/user message text (static-content) | 🧪 backstop | `whitespace-pre-wrap break-words` on bubble text; no markdown rendering — LLM prose displays as plain wrapped text, preserving line breaks only |
| zero-one-many | Inline action pills per message | ✅ covered | Zero actions → no pill row renders under that message; one or many → a vertical stack of pills, one per action, in the order the response listed them |
| long-text | Message input field | 🧪 backstop | Single-line `<input>`; very long input scrolls horizontally within the field per native browser behavior — no custom multi-line textarea for this phase's scope |
