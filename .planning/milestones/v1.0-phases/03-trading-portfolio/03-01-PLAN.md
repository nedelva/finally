<objective>
**As a** FinAlly user, **I want to** buy and sell shares of a watched ticker at the live streaming
price with an instant fill, **so that** my $10,000 virtual portfolio actually responds to the market
I am watching.

This is the phase's tracer slice: the thinnest path that touches every layer Phase 3 will modify -
SQLite write, repository function, FastAPI route, REST client, React form - wired end-to-end and
proven by a real integration test. Every later plan in this phase expands outward from the engine
this plan lands.

Purpose: PORT-02 and PORT-03 are the reason the phase exists; nothing else in Phase 3 is observable
until a trade can actually execute. The post-trade `portfolio_snapshots` write (PORT-06's
immediate-after-each-trade half) lands here too because it must share the trade's single SQLite
transaction - splitting it out would mean re-opening the most safety-critical function in a later
wave.

Output: `POST /api/portfolio/trade`, `GET /api/portfolio`, the repository trade engine behind them,
and a working trade bar in the terminal UI.
</objective>

  <action>
Extend `backend/app/db/repository.py` with four module-level sync functions following the file's
existing conventions (own connection per call, `?` placeholders, `with conn:` for writes,
`finally: conn.close()`, `ValueError` for caller-level conditions):

`get_cash_balance() -> float` reads `users_profile.cash_balance WHERE id = ?` bound to
`DEFAULT_USER_ID`. `get_positions() -> list[dict]` selects `ticker, quantity, avg_cost, updated_at`
from `positions WHERE user_id = ?` ordered by `ticker`, returning `[dict(row) for row in rows]`.

`total_portfolio_value(conn, price_cache) -> float` takes an already-open connection so it can run
inside a live transaction. It reads `cash_balance` and every `positions` row from that connection and
returns `round(cash_balance + sum_of_position_values, 2)`, where each position's contribution is
`round(quantity * current_price, 2)` and `current_price` is `price_cache.get_price(ticker)` falling
back to that row's own `avg_cost` when `get_price` returns `None` (D-03). The rounding is specified
to the digit on purpose: `build_portfolio` below must use the identical per-position round-then-sum
order, because rounding each position before summing and rounding only the total produce different
cents for fractional quantities, and the snapshot-equals-REST truth this plan asserts is only
provable when both sides do the same arithmetic. This helper is the valuation path shared by the
in-transaction post-trade snapshot and 03-04's `record_snapshot`.

`execute_trade(price_cache, ticker, side, quantity) -> dict` is the transactional core. It expects an
already-normalized ticker, exactly as `add_watchlist_ticker` does — that function's docstring fixes
the convention that the normalize-and-validate gate lives at the API boundary and not in the
repository, so the route handler does it and this layer does not import from `app.market`. Raise
`ValueError` when `quantity` is zero or negative, before any arithmetic. Open one connection and do
everything else inside one
`with conn:` block so validate-then-write is atomic against a concurrent caller: (a) a
`SELECT 1 FROM watchlist WHERE user_id = ? AND ticker = ?` membership gate on this same `conn` —
D-01's enforcement point, and it must run on the transaction's own connection rather than calling
`get_watchlist()`, which would open a second connection and reopen the read-then-write race; (b)
`SELECT cash_balance FROM users_profile WHERE id = ?`; (c) `SELECT quantity, avg_cost FROM positions
WHERE user_id = ? AND ticker = ?`. Read the fill price from `price_cache.get_price(ticker)` and
raise `ValueError` if it is `None`.

Buy path: `cost = round(price * quantity, 2)`; raise `ValueError` with the copy
"Insufficient cash for this trade. Lower the quantity and try again." when `cost` exceeds the
balance; `new_qty` is the prior quantity plus `quantity`; recompute the weighted average as
`round(((prior_quantity * prior_avg_cost) + cost) / new_qty, 4)`; `new_cash = round(balance - cost, 2)`.
Sell path: raise `ValueError` with "You don't own enough shares to sell that many. Lower the
quantity and try again." when `quantity` exceeds the held amount by more than `1e-9`;
`new_cash = round(balance + round(price * quantity, 2), 2)`; carry the prior `avg_cost` through
untouched — it is a buy-only quantity, and recomputing it here corrupts every later P&L figure.

Then write, still inside the same block: `UPDATE users_profile SET cash_balance = ?`; when `new_qty`
is at or below `1e-9` a `DELETE FROM positions WHERE user_id = ? AND ticker = ?`, otherwise an
`INSERT INTO positions (...) VALUES (...) ON CONFLICT (user_id, ticker) DO UPDATE SET quantity =
excluded.quantity, avg_cost = excluded.avg_cost, updated_at = excluded.updated_at` against the
existing `UNIQUE (user_id, ticker)` constraint; an `INSERT INTO trades` row with a fresh
`str(uuid.uuid4())` id, the side, the quantity, the fill price and an ISO
`datetime.now(UTC).isoformat()`; and finally an `INSERT INTO portfolio_snapshots` row whose
`total_value` comes from `total_portfolio_value(conn, price_cache)` (PORT-06's immediate-after-trade
half). Return a dict carrying the executed trade's `id`, `ticker`, `side`, `quantity`, `price` and
`executed_at`, matching the `Trade` interface in `frontend/lib/types.ts`.

Create `backend/app/api/portfolio.py` mirroring `backend/app/api/watchlist.py`'s structure. Declare
`TradeRequest(BaseModel)` with `ticker: str`, `side: Literal["buy", "sell"]` and `quantity: float`.
Declare `build_portfolio(price_cache) -> dict` mirroring `build_watchlist`'s join-persisted-rows-with-
the-cache shape: for each `get_positions()` row take `price_cache.get_price(ticker)`, fall back to
that row's `avg_cost` when it is `None` (D-03), compute `market_value` as
`round(quantity * current_price, 2)`, `unrealized_pnl` as
`round((current_price - avg_cost) * quantity, 2)`, and `unrealized_pnl_percent` as
`round((current_price / avg_cost - 1) * 100, 4)` guarded by `avg_cost > 0`. Its `total_value` is
`round(cash_balance + sum of the already-rounded per-position market_value values, 2)` — the same
round-then-sum order `total_portfolio_value` uses, which is what makes the two agree to the cent —
and `total_unrealized_pnl` is the rounded sum of the per-position figures. Every emitted key must
match `Position` and `Portfolio` in `frontend/lib/types.ts` exactly.

Declare `create_portfolio_router(price_cache) -> APIRouter` building a fresh
`APIRouter(prefix="/api", tags=["portfolio"])`. `GET /portfolio` returns
`await asyncio.to_thread(build_portfolio, price_cache)`. `POST /portfolio/trade` first normalizes
`body.ticker` with `normalize_ticker` from `app.market`, mirroring `post_watchlist_route`'s own
normalize-then-act ordering, then wraps
`await asyncio.to_thread(execute_trade, price_cache, normalized, body.side, body.quantity)` in
`try/except ValueError`, returning `JSONResponse(status_code=400, content={"success": False,
"error": str(exc)})` on failure. On success it fetches the refreshed portfolio with a second
`await asyncio.to_thread(build_portfolio, price_cache)` on its own line — every repository-backed
call in an `async def` goes through `to_thread` per `repository.py`'s module docstring, so calling
`build_portfolio` inline inside the response literal would block the event loop — and returns
`JSONResponse(status_code=200, content={"success": True, "trade": result, "portfolio": portfolio})`.
The 400 body carries no `portfolio` key — `TradeErrorResponse` in types.ts declares only `success`
and `error`.

Export the new names: add `get_cash_balance`, `get_positions`, `execute_trade` and
`total_portfolio_value` to the import line, the docstring's Public API list and `__all__` in
`backend/app/db/__init__.py`; add `create_portfolio_router` to the same three places in
`backend/app/api/__init__.py`. In `backend/app/main.py` import `create_portfolio_router` from
`app.api` and add `app.include_router(create_portfolio_router(price_cache))` immediately after the
existing watchlist router line — it must sit above the `StaticFiles` mount, which matches everything
by prefix.

Do not add any restriction to `DELETE /api/watchlist/{ticker}`: per D-04 removal stays unrestricted,
and the D-03 fallback is what keeps a held-but-unwatched position displaying honestly.
