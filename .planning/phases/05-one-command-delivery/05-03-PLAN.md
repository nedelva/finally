<objective>
Make the shipped image's dependency story honest: the terminal demo's `rich` dependency stops
masquerading as a runtime requirement, and the Polygon SDK stops being a module-load requirement for
the simulator path that most operators will actually run.

Purpose: an operator who reads `pyproject.toml` to understand what FinAlly needs should see what
FinAlly actually needs. This is the CONCERNS.md dependency-hygiene work the ROADMAP scope notes
require for Phase 5 ("so the shipped image is honest").

Output: a `demo` optional-dependency extra, a regenerated lockfile, a lazily-importing
`MassiveDataSource`, and the mandatory companion test fix without which the suite breaks.

**A verified constraint the executor must not fight.** `rich` arrives transitively regardless:
`uv tree` in `backend/` shows `litellm` → `tokenizers` → `huggingface-hub` → `typer` → `rich
v14.3.2`. Moving `rich` out of the core `dependencies` array therefore changes the **declared**
contract, not the installed set — `import rich` will still succeed inside the container, and that is
correct, not a bug. Do not attempt to prune it; the only way to would be dropping `litellm`, which
PLAN.md section 9 locks. Do not write, and do not "fix" toward, any check asserting that `rich`
cannot be imported at runtime.
</objective>

  <action>
Remove both module-scope SDK imports from `backend/app/market/massive_client.py` — the one binding
`RESTClient` and the one binding `SnapshotMarketType` — and add `from typing import TYPE_CHECKING`
to the remaining stdlib imports. Under a module-scope `if TYPE_CHECKING:` block, re-import
`RESTClient` from `massive` for type-checking only, so the `self._client: RESTClient | None`
annotation on line 40 still resolves under ruff without requiring the SDK at module-load time. The
file already has `from __future__ import annotations`, so the annotation is a string at runtime and
needs no quoting.

Move the real imports into the two methods that actually touch the SDK: `start()`, as its first
statement, before constructing the client; and `_fetch_snapshots()`, as its first statement, before
referencing `SnapshotMarketType.STOCKS`. This is safe because `MassiveDataSource` is only ever
constructed by `create_market_data_source()` when `MASSIVE_API_KEY` is non-empty — by the time
`start()` runs, the caller has already committed to the Massive path, so a genuine missing-SDK error
is exactly as loud as today's, merely deferred to the moment it matters.

**Companion edit, mandatory and in this same commit.** Removing the module-level binding deletes the
attribute `app.market.massive_client.RESTClient`, which three tests patch. Re-point all three
`with patch("app.market.massive_client.RESTClient"):` context managers in
`backend/tests/market/test_massive.py` to `with patch("massive.RESTClient"):`. This works because
the deferred import re-reads the attribute from the `massive` module at call time, so patching the
SDK's own namespace still intercepts construction. Without this edit the three tests raise
`AttributeError: <module 'app.market.massive_client'> does not have the attribute 'RESTClient'`.

Leave `backend/app/market/factory.py` unchanged unless ruff reports an unresolved name there —
importing the `MassiveDataSource` class does not touch `massive` once the SDK imports are deferred.
If ruff does flag something, apply the minimum fix and record it in the summary.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| declared manifest → installed image | What `pyproject.toml` says the app needs determines what an auditor believes is in the image; a divergence is a trust failure even when it is not exploitable |
| module import graph → external SDK | A module-scope third-party import executes vendor code on every app boot, including on paths that never use that vendor |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-05-03 | Tampering | production image dependency surface | medium | accept | Moving `rich` to a `demo` extra makes the **declared** contract honest, but it does not shrink the installed set: `uv tree` in `backend/` shows `rich v14.3.2` arriving transitively via `litellm` → `tokenizers` → `huggingface-hub` → `typer`.
