<objective>
Let the user remove a ticker. This closes the watchlist loop the tracer opened and 02-02 half-filled:
the row list, already REST-driven and therefore shrinkable, now actually shrinks — and the ticker
stops streaming.

Satisfies WTCH-02 and ROADMAP success criterion 2.

Purpose: a list you can only add to is not a watchlist the user controls.
Output: `DELETE /api/watchlist/{ticker}`, a per-row remove affordance, the empty state, and the
main-chart selection guard that stops the chart freezing on a removed ticker.
</objective>

  <action>
Add `remove_watchlist_ticker(ticker: str) -> bool` to `backend/app/db/repository.py`. It deletes the
`watchlist` row matching `DEFAULT_USER_ID` and the given already-normalized ticker, and returns
whether a row was actually deleted — read the cursor's `rowcount` to decide. Returning a boolean
rather than raising keeps this consistent with the project's convention that absence is a return
value, not an exception, and gives the route what it needs to distinguish 204 from 404. Bind both
values through the `execute()` parameter tuple with `?` placeholders.

The statement must target the `watchlist` table only. Removing a ticker from the display list must
never cascade into `positions`, `trades`, `portfolio_snapshots`, or `chat_messages` — those tables
exist from plan 02-01 and Phase 3 will fill them, and a user tidying their watchlist must not be able
to destroy holdings or history as a side effect.

Register `DELETE /api/watchlist/{ticker}` on the router in `backend/app/api/watchlist.py`, mirroring
the POST handler's shape as an `async def` closure taking the path parameter and `Request`:
1. `normalized = normalize_ticker(ticker)` — so a lowercase path segment still resolves.
2. `removed = await asyncio.to_thread(remove_watchlist_ticker, normalized)`.
3. When `removed` is false, return a 404 `JSONResponse` carrying an `error` key naming the ticker, and
   return without notifying — nothing changed, so the data source must not be told anything did.
4. Otherwise `await request.app.state.market_source.remove_ticker(normalized)` and return 204 with no
   body. The frontend's `removeWatchlistTicker` explicitly special-cases 204 and will not attempt to
   parse a body, so do not send one.

Do not add a "still-held position" guard before the `remove_ticker` call. The sibling-branch prior art
has one, but nothing writes the `positions` table until Phase 3, so it would be permanently dead code
with no test able to exercise it. 02-RESEARCH.md records this as assumption A3 and has already filed a
durable note in `.planning/codebase/CONCERNS.md` so Phase 3 rediscovers the nuance independently.

Tests. Extend `backend/tests/db/test_repository.py` with synchronous tests for a successful delete
returning true, a delete of an absent ticker returning false, and a second delete of the same ticker
returning false. Extend `backend/tests/api/test_watchlist.py` with `remove`-named tests covering the
204 happy path (asserting the fake source recorded exactly the normalized ticker), the lowercase path
parameter, the 404 absent case asserting `remove_ticker` was NOT recorded and the row count is
unchanged, the repeated-delete case, and a test asserting that after a removal the row counts in
`positions`, `trades`, `portfolio_snapshots`, and `chat_messages` are all still zero.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `DELETE /api/watchlist/{ticker}` | Untrusted user-supplied path parameter crosses into the process |
| `app/api` → `app/db` | The path value crosses into SQL statement execution |
| `app/api` → `MarketDataSource` / `PriceCache` | The path value becomes a dict key for removal |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-09 | Tampering | `remove_watchlist_ticker` SQL | high | mitigate | The ticker is bound as a `?` placeholder parameter, never interpolated into SQL text. Enforced by the `ruff check --select S608` gate on Task 1. |
| T-02-10 | Tampering | path traversal via `{ticker}` | medium | mitigate | FastAPI URL-decodes the path parameter, but the value is only ever used as a SQL bind parameter and a dict key — never as a filesystem path — so traversal does not apply here. `normalize_ticker` is still applied before use as defense in depth. |
| T-02-11 | Tampering | unintended cascading delete | high | mitigate | The DELETE statement targets the `watchlist` table only. Task 1 asserts that after a removal the `positions`, `trades`, `portfolio_snapshots`, and `chat_messages` row counts are unchanged, so a watchlist edit can never destroy holdings or history. |
| T-02-12 | Repudiation | no removal audit trail | low | accept | Single-user simulated environment with no compliance requirement; PLAN.md specifies an append-only log for `trades` only, not for watchlist edits. |

Package legitimacy: not applicable — this plan installs nothing.
