<objective>
**As a** FinAlly user, **I want to** tell the assistant to buy, sell, or change my watchlist in plain
language and watch it happen, **so that** I can run the whole terminal from the conversation instead
of hunting for the right control.

This plan expands the 04-01 tracer outward: the same `POST /api/chat` route and the same panel now
carry actions. It also closes the held-position watchlist-removal gap that `.planning/codebase/CONCERNS.md`
and 04-RESEARCH.md Open Question 1 both flagged — the guard goes into the shared repository function
so the manual `DELETE` route and the new chat path inherit it together, which is exactly why it
lands in the plan that introduces the second call site rather than a separate cleanup pass.

Purpose: CHAT-03, CHAT-04 and CHAT-05 are what make this an agent rather than a chatbot. The
load-bearing constraint is that none of it introduces new business logic — every mutation goes
through the Phase 2/3 functions unchanged, so the assistant is strictly bounded by what the user
could already do by hand.

Output: a chat dispatch loop that executes watchlist changes then trades, reports each one
individually as executed or failed, and renders both as inline pills in the conversation.
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` — the ROADMAP scope note "AI-initiated trades reuse the exact Phase 3
validation path — no second, looser execution route" marks the point where watchlist mutation and
trade execution stop having a single caller. Until this plan, `remove_watchlist_ticker()` had exactly
one call site (`delete_watchlist_route`); from this plan it has two (that route plus the chat
dispatch loop).

**Question:** when the second caller arrives, does the held-position rule get *promoted* into the
shared function, or *added alongside* in the new caller only?

**Decision: promote.** The guard lives inside `remove_watchlist_ticker()` (D-02). Both call sites
inherit it; neither can diverge. This is recorded rather than assumed because the alternative —
guarding only the chat path — was genuinely on the table: the manual `DELETE` route has carried the
same gap since Phase 2, and fixing only the new path would have been the smaller diff. It was
rejected because it would create exactly the behavioural split the phase's own scope note forbids:
the assistant would refuse a removal the user could still perform by hand one panel over.

**Identity model, unchanged:** `remove_watchlist_ticker(ticker)` keeps its signature and its
`DEFAULT_USER_ID` binding. No caller-kind parameter, no `force=` escape hatch, no per-caller policy
argument — the rule is a property of the operation, not of who asked for it. This checkpoint is
advisory; it records the decision and does not gate the phase.
</assumption_delta_decision>

  Add the held-position guard to `remove_watchlist_ticker` in `backend/app/db/repository.py`, and
  give the DELETE route the matching translation.

  **The guard.** Inside the existing `with conn:` block, before the `DELETE`, open the transaction
  with `conn.execute("BEGIN IMMEDIATE")` and then `SELECT quantity FROM positions WHERE user_id = ?
  AND ticker = ?` bound to `DEFAULT_USER_ID` and the ticker. If a row comes back with `quantity`
  greater than `1e-9`, raise `ValueError` with a message naming the ticker and the held quantity and
  telling the user to sell first. If no row comes back, or the row's quantity is at or below `1e-9`,
  fall through to the existing `DELETE` and the existing `cursor.rowcount > 0` return unchanged.

  The `BEGIN IMMEDIATE` escalation is load-bearing and is the same one `execute_trade` uses: this
  function now reads (`positions`) before it writes (`watchlist`), and sqlite3's default deferred
  transaction only opens on the first *write*, so without the escalation a concurrent buy could
  commit between the guard's `SELECT` and the `DELETE`, removing a ticker that is held by the time
  the delete lands. Carry across the substance of the WR-01 comment in `execute_trade` explaining
  why, rather than leaving the escalation looking incidental.

  The `1e-9` literal is copied from `execute_trade`'s own close-out check (D-03), with the same
  comparison direction: above `1e-9` means still held, at or below means not held. Do not introduce
  a named constant in this plan and do not pick a different value — a second, subtly different
  threshold is exactly how a ticker becomes permanently unremovable.

  convention for a caller-level rejection, the same one `add_watchlist_ticker` uses for a duplicate
